# Проверка архитектуры перед разработкой

12 сентября 2026 года. Проверена версия 0.5 ТЗ; результат закреплён в версии 0.6. Проверка охватывает документы и согласованность проектных решений. Приложение пока не реализовано; нагрузочные, интеграционные и восстановительные испытания не выполнялись.

Дополнение версии 0.7: пользователь выбрал GPT-5.6 Luna с reasoning.effort=medium через прямой OpenAI API. Выбор закреплён в ADR-17; OPEN-02 сужен до отдельной ASR модели и проверки интеграции. Факт выбора не означает, что корпус качества уже пройден.

До проверки архитектура была описана как рекомендуемый набор компонентов. Этого было недостаточно для начала финансового ядра: механизм конкуренции, очередь, физические ограничения, отзыв доступа при восстановлении и некоторые маршруты оставались выбором исполнителя. Теперь они определены в [ARCHITECTURE.md](ARCHITECTURE.md) и [DATA_CONTRACT.md](DATA_CONTRACT.md).

## 1 Обнаруженные пробелы и решения

| № | Что могло привести к ошибке | Что зафиксировано | Состояние |
|---|---|---|---|
| H01 | «Блокировать строки либо выбрать уровень изоляции» допускает разные несовместимые реализации | READ COMMITTED, workspace lock, фиксированный порядок, проверка версии после lock, повторы целой транзакции | Решение зафиксировано, ADR-04 |
| H02 | После исправления можно сложить старую и новую сумму или потерять движение счёта | Неизменяемые ревизии, обратные AccountEntry, current revision для отчёта | Решение зафиксировано, ADR-03 |
| H03 | Подтверждение webhook или задача в памяти не переживает падение | Inbox+Job до 2xx, аренды в PostgreSQL, outbox и отдельные consumer receipts | Решение зафиксировано, ADR-05 |
| H04 | AI завершится после ручного ввода или исключения участника | Постоянный Candidate, expected draft version, lease token и повторная авторизация | Решение зафиксировано, ADR-06/08 |
| H05 | Один FK по ID и забытый WHERE могут связать разные семьи | Составные FK, RLS с локальным контекстом и отдельные runtime/migration роли | Решение зафиксировано, ADR-06 |
| H06 | Подписанная storage ссылка продолжает давать данные после выхода | Серверная авторизованная выдача; отдельно отмечен предел отзыва уже полученных данных | Решение зафиксировано, ADR-11 |
| H07 | Backup возвращает бывшего участника или старого администратора | Независимый журнал SecurityChange, fence, подтверждение после двух контуров, закрытый restore | Решение зафиксировано, ADR-14 |
| H08 | Исполнитель сам выбирает месяцы/30 дней, создаёт дубли периодов | DATE, исходный anchor, exclusion constraint, ensure_periods и версии шаблона | Решение зафиксировано, ADR-07 |
| H09 | Смешанный чек и фильтры/метки размножают суммы | Фильтры частей в одной allocation, EXISTS для tags, раздельный итог выборки/чека | Решение зафиксировано, ADR-09 |
| H10 | Личная карта с частью расходов выглядит как точный баланс | full_tracking/reference, CashLeg, opening cutoff и отдельная полнота | Решение зафиксировано, контракт данных |
| H11 | Возвраты и частичная оплата теряют категорию, резерв или остаток обязательства | Связи с конкретными частями и эффектом, явное решение о резерве, жизненный цикл occurrence | Решение зафиксировано, контракт данных |
| H12 | Общая стоимость AI превышается параллельными запросами/повторами | Атомарная резервация предельной стоимости, квоты и счётчики попыток | Решение зафиксировано, ADR-12 |
| H13 | В меню есть действие, серверный путь или право не определены | CMD-01–31, текущие права, версии, подтверждения, эффекты и ошибки | Решение зафиксировано, контракт данных |
| H14 | Производительность и надёжность заявлены без проверки окружения | Явные SLO, размеры пакетов, пулы, план нагрузки и условия выпуска | Критерии зафиксированы; результаты отсутствуют |
| H15 | «99% суммы» позволяет выпустить известный опасный класс автозаписи | Раздельная оценка модели/кандидата/записи и блокировка известной ошибки этого класса | Критерий зафиксирован, ADR-08 |
| H16 | Выбор хостинга, модели и патчей смешан с незавершённостью денежной модели | Ядро фиксировано; в 0.7 LLM/vision выбраны по ADR-17; ASR и окружение имеют отдельные сроки | См. раздел 4 |

Согласованность прежнего [SPEC_REVIEW](SPEC_REVIEW.md): R01–R11 закрыты **на уровне контрактов P0** или получили явную границу P1/P2. В частности, оплата одного чека несколькими источниками не проводится автоматически в P0; полный интерфейс этого сценария требует отдельного расширения. R12 закрыт в части сервисной квоты; режим аудитории выбирается перед размещением. Предложения F01–F06 прежнего аудита остаются предложениями к объёму и не включены в P0 автоматически.

## 2 Что даёт и чего не доказывает проверка

Финансовое ядро теперь имеет единый порядок записи, схему исправлений, контракт периодов, права команд и механизмы восстановления. Можно начинать реализацию модулей с ручного вертикального среза, не делегируя разработчику выбор этих правил.

Архитектурное решение не доказывает отсутствие ошибок кода, достижение задержек, совместимость всех конкретных пакетов и пригодность AI на русских чеках. Для этого нужны следующие сценарии. Их формулировки являются критериями приёмки; ни один не помечен как уже пройденный.

## 3 Дополнительная архитектурная приёмка

Общий статус AR-01–AR-36: **не выполнено — требуется реализация**. Это дополнение к A01–A230 и числовым примерам [ACCEPTANCE](ACCEPTANCE.md), не их замена. Все AR ниже обязательны для P0, кроме явно указанной будущей части P1.

| ID | Проверка | Ожидаемый результат |
|---|---|---|
| AR-01 | Одинаковый update 100 раз, включая конкурентную доставку | Один inbox, один логический результат; при нескольких кандидатах ровно по одной операции на каждого |
| AR-02 | Убить API до commit inbox и после commit до HTTP ответа | До commit нет 2xx; повтор после commit не создаёт вторую Job/операцию |
| AR-03 | Убить worker после ledger commit до отправки ответа | Расход один; доставка восстанавливается по outbox |
| AR-04 | Аренда истекла, второй worker завершил, первый вернулся с AI результатом | Старый lease token не принимается; второй финансовый эффект не появился |
| AR-05 | Ручная правка с 700 на 650, затем поздний AI ответ 700 | Итог 650, один candidate/transaction; ручное значение сохранено |
| AR-06 | Два ожидающих вопроса, свободное «500», ответ на закрытую карточку | Нет случайной записи в чужой вопрос; нужен выбор; закрытый вопрос не изменяет другой черновик |
| AR-07 | Две правки одного расхода с одной expected_version | Одна успешная, другая 409; обе стороны получают актуальное состояние |
| AR-08 | Исключение участника соревнуется с проведением его расхода | Результат соответствует порядку workspace lock; после отзыва проведение невозможно |
| AR-09 | Два входа по последнему использованию кода; повтор входа уже участника | Одно новое членство; квота не отрицательна; технический повтор не расходует использование |
| AR-10 | Два одновременных предложения передачи роли | Один администратор; старое предложение не применяется к новой ACL версии |
| AR-11 | Смешать бюджет, категорию, счёт, person и operation ID разных семей | API запрещает; составные FK запрещают ошибочную запись и из сервисного SQL |
| AR-12 | Bootstrap моих бюджетов, затем пул переиспользует соединение A для B без/с новым контекстом | Bootstrap раскрывает только собственные метаданные; финансовые данные без контекста закрыты; B не видит A; write policy не наследует исключение SELECT |
| AR-13 | Member запрашивает чужой черновик/голос и общий чек; worker системного обзора читает черновики | Частный материал недоступен, общий подтверждённый чек доступен; обзор получает только разрешённый счётчик ожиданий |
| AR-14 | Выход/rejoin, старая кнопка, cached idempotency result и старая ссылка экспорта | Старое поколение не оживает; каждый запрос повторно авторизуется; ранее скачанную копию система не объявляет удалённой |
| AR-15 | Исходный остаток 10000, расход1000→800, заметка, void, restore | Последовательность балансов 9000→9200→9200→10000→9200; расход в отчёте 800 |
| AR-16 | Случайные последовательности переводов, исправлений, отмен и восстановлений | Деньги в minor units; обратный эффект точен; reference/unknown не превращаются в полный банковский баланс |
| AR-17 | Два возврата одновременно исчерпывают одну часть чека | Нельзя превысить возвращаемую сумму; категория/получатель и период возврата корректны |
| AR-18 | Возврат покупки из цели и отмена/изменение связанной исходной покупки | Резерв меняется только по выбранному действию; конфликтующие зависимости не остаются |
| AR-19 | Смешанный чек 1000 Продукты/Софа +400 Дом/Ниджат, несколько tags | Продукты+Ниджат=0; Продукты=1000, полный чек=1400; tags не умножают суммы |
| AR-20 | Opening cutoff, импорт до него, поздняя правка до сверки, только заметка | Нет двойного движения; денежная правка делает сверку stale; заметка не меняет баланс/сверку |
| AR-21 | Личная карта reference, неизвестная валюта чека, заполненный бюджет и смена валюты | Нет выдуманного остатка/конвертации; смена подписи валюты запрещена |
| AR-22 | Платёж1000 оплачен600, переход периода, доплата/переплата, правка серии | Остаток400 один раз; изменения факта и ожидания различимы; исполненные экземпляры не переписаны |
| AR-23 | Управляемое время: 10–9, 31 января, високосность, fixed_days и DST | Точные ожидаемые границы без дрейфа; каждое поддерживаемое событие относится к одному периоду |
| AR-24 | Несколько scheduler, простой на несколько периодов и конкурентная смена политики | Уникальные смежные периоды по действующим версиям; старый шаблон не перезаписывает принятый план |
| AR-25 | План отсутствует, AI недоступен, доход известен только за месяц, период14 дней | Период и ручной учёт работают; лимит не становится нулём, доход не копируется целиком |
| AR-26 | Выгрузка/AI читают отчёт во время исправления; затем поздний ответ анализа | Один числовой снимок, явная версия; устаревшее предложение не выполняется |
| AR-27 | Upload удался, DB registration упал; удаление объекта упало; опасный/огромный файл | Повтор безопасен; staging и удаление доводятся до конца; ограничения действуют до платного AI |
| AR-28 | Один import повторён после сбоя, rollback с зависимым возвратом, слишком большой пакет | Нет второго импорта; откат проверяет связи; частичный большой импорт не называется атомарным |
| AR-29 | Два AI запроса расходуют остаток общей квоты; provider timeout и retry | Резервации атомарны; неизвестная стоимость не освобождается без сверки; повтор требует новой резервации |
| AR-30 | Один получатель заблокировал бота, другой получил; timeout sendMessage; 429 | Независимые статусы, retry_after; ledger не дублируется; предел гарантии сообщения соблюдён |
| AR-31 | Остановить SecurityChange на каждом из пяти шагов, включая недоступный/неполный журнал | Успех не объявляется раньше конца; fence и повтор восстанавливаются; prepared не удаляет данные сам; без доказуемой последней версии доступ закрыт |
| AR-32 | Restore backup до выхода, исключения, передачи admin и удаления бюджета | До доступа применены committed ACL; неопределённое в карантине; старые коды/сессии не действуют |
| AR-33 | Полный restore из реально доступного backup/WAL и проверка ссылок на вложения | Измеренные RPO≤1 час/RTO≤4 часа; хвост риска указан; финансовые инварианты проверены |
| AR-34 | Нагрузка ТЗ, один горячий бюджет, 50 000 операций, расширенные фильтры | Измерены p95, lock waits, очередь и пул; нет потерь/дублей, backlog восстанавливается |
| AR-35 | Выпуск с jobs предыдущего формата, миграция со старого снимка и откат приложения | Совместимые schema versions; нет разрушительного отката денег; неизвестный payload отклонён явно |
| AR-36 | Корпус AI на выбранном профиле: сырая ошибка, уточнение, ошибочная автозапись, инструкция в заметке, недоступность провайдера | Использованы gpt-5.6-luna, medium и прямой OpenAI API по ADR-17; ошибки этапов разделены, опасная автозапись блокирована, скрытая подмена профиля отсутствует |

При AR-34 внешние задержки измеряются отдельно. При контролируемом stub провайдера проверяется пропускная способность собственной системы; затем на ограниченном реальном корпусе проверяются фактические интеграционные задержки и стоимость. Stub не доказывает качество модели.

Файловые и HTTP проверки P1 дополняются в момент выпуска Mini App: проверка initData, CSRF, cookie в реальных клиентах Telegram, новые права и обход старой сессией. Финансовые AR-01–36 остаются обязательными независимо от интерфейса.

## 4 Решения, зависящие от окружения

| ID | Что ещё не выбрано | Когда и как закрывается | Можно ли начинать ядро |
|---|---|---|---|
| OPEN-01 | Страна использования, страна размещения, поставщик compute/DB/storage | До переноса личных данных: доступность, нужные сервисы, восстановление, условия обработки и стоимость | Да, через адаптеры и локальную среду |
| OPEN-02 | Конкретная модель ASR; проверка уже выбранного профиля LLM/vision | GPT-5.6 Luna Medium через OpenAI API выбрана; до пилота выбрать транскрипцию, проверить интеграцию и корпус, условия данных и стоимость | Да, с зафиксированным Luna адаптером и тестовым ASR |
| OPEN-03 | Точные package patch versions и digest образов | В первом bootstrap: lockfile, совместимый запуск, миграции и smoke проверки на выбранных линиях | Да; это первый технический шаг |
| OPEN-04 | Аудитория размещённого бота: открытый /start или закрытый пилот; суммы сервисных квот | До включения production webhook; сохраняется создание/вступление по заданной конфигурации | Да, продуктовый поток создания остаётся |
| OPEN-05 | Домен, секреты, канал и ответственный за эксплуатационные события | До пилота; проверка ротации, доступности и учебного восстановления | Да |
| OPEN-06 | Валюта, реальный охват счетов и начальная точка конкретного бюджета | В пользовательском мастере; это настройки данных, а не смена архитектуры | Да |

Ни страна, ни реальная валюта не выводятся из русского языка. Основной AI провайдер OpenAI уже выбран пользователем; страна размещения и ASR уточняются отдельно. Выбор провайдера не подменяет денежные правила. Удалённый сервис не подключается в рамках подготовки этих документов.

## 5 Условия перехода к разработке и выпуску

| Этап | Условие | Текущий результат |
|---|---|---|
| Архитектурная основа | ADR-01–17, контракт денег/данных/команд, согласованность с FR и сценариями | Документы подготовлены; автоматические проверки структуры и локальных ссылок выполнены |
| Bootstrap | Точные версии, скелет модулей, CI, реальные SQL migrations и RLS | Не выполнено |
| Ручное ядро | Создание → вступление → расход → правка → следующий период → общий отчёт | Не выполнено |
| Надёжность | Гонки, retry/fencing, ограничения схемы, изоляция и SecurityChange | Не выполнено |
| Интеграции | Telegram/ASR/vision/LLM, стоимость и деградация | Не выполнено |
| Пилот | Приёмка A/AR, восстановление, нагрузка, удаление, выбранная среда | Не выполнено |

Перед первой пользовательской эксплуатацией должны быть сохранены отчёты испытаний с версиями кода, схемы, модели, конфигурации и выборки. Галочка напротив документа не заменяет успешную проверку. Существующая оценка 45–72 дня относится к версии 0.4; календарь 0.5 и конкретизированная надёжность 0.6 требуют обновления оценки после разбиения на реализационные срезы.
