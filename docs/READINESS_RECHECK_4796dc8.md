## Подтверждённые дефекты

### RC-01 · P1 · Возврат чужой доли теряется при правке и восстановлении

Покупка создаёт долг 1500 ₽; продавец возвращает из него 500 ₽, остаётся 1000 ₽.
Изменение только комментария самого возврата либо его отмена с восстановлением
возвращает долг к **1500 ₽**. Исправление возврата с 500 на 300 ₽ также даёт
1500 ₽ вместо **1200 ₽**.

Поиск зависимых требований теперь включает `reversal`, но новый эффект
создаёт ReceivableEntry только для `RECEIVABLE_DECREASE`. При новой ревизии
старый эффект отключается, а возвратная запись для нового эффекта не появляется.
[Пропущенная ветка](../src/fintracker/application/ledger/service.py:771).
Нужно восстанавливать и пересчитывать возвратную составляющую эффекта по
связям частей исходной покупки при revise/restore, с учётом изменения суммы.

Тест: `test_refund_of_foreign_share_keeps_effect_after_revision`, 3 варианта.

### RC-02 · P1 · Удалённая доля ошибочно считается полученным возмещением

Первое исправление смешанной покупки на полностью свою теперь проходит.
Но после этого нельзя ни изменить комментарий, ни отменить покупку: сервис
утверждает, что получено возмещение, которого не было.

Исправление оставляет положительный `original_minor` и обнуляет outstanding,
а guards по-прежнему вычисляют получение как `original - outstanding`.
[Закрытие проекции](../src/fintracker/application/ledger/service.py:715),
[guard исправления](../src/fintracker/application/ledger/service.py:639),
[guard отмены](../src/fintracker/application/ledger/service.py:595).
Унифицировать определение реально полученной суммы по активным движениям;
отменённое основание требования и погашение должны различаться во всех guards.

Тест: `test_removed_share_does_not_block_later_correction`, 2 варианта.

### RC-03 · P1 · Регрессия: нельзя исправить сумму связанного платежа

Ранее проходивший сценарий: обязательство 1000 ₽ полностью оплачено, затем
фактическая сумма операции исправляется на 500 ₽. Ожидается частичная оплата
500 ₽, но текущий код возвращает ConflictError и откатывает правку.

Для сохранения частичной связи при изменении заметки сумму связи теперь
оставляют неизменной при любой правке. Это ломает денежную коррекцию полной
оплаты. [Проверка](../src/fintracker/application/ledger/service.py:864).
Нужны отдельные правила неденежной правки и согласованного изменения денег,
с проверкой распределений по всем связанным обязательствам.

Тест из прежнего аудита, без изменения ожидания:
`test_revised_scheduled_payment_recomputes_obligation_coverage`.

### RC-04 · P1 · Повтор после очистки pending меняет тип команды

«Выделить резерв» → `5000`: резерв записан, pending удалён, затем процесс
падает до сохранения ответа. Повтор того же IncomingMessage с тем же message_id
создаёт **новый черновик расхода на 5000 ₽**, вместо повторения результата
резервирования. Автоматическое проведение расхода этим тестом не утверждается.

Добавленный reason-key проверяется лишь после маршрутизации в цель. Когда
pending уже удалён, эта ветка недоступна и вход снова разбирается как расход.
[Вызов и отдельная очистка](../src/fintracker/application/conversation/service.py:434),
[очистка перед возвратом ответа](../src/fintracker/application/conversation/service.py:468).
Нужен долговечный результат команды по source key, доступный до выбора маршрута;
эффект, завершение ожидания и результат должны согласованно фиксироваться.

Тест: `test_goal_retry_after_pending_cleanup_keeps_original_command`.

### RC-05 · P2 · Свободный reason ошибочно стал ключом идемпотентности

Два отдельных сервисных вызова выделения 100 и 200 ₽ с одинаковым пояснением
«Еженедельный взнос» дают **100 ₽ вместо 300 ₽**. Второй вызов молча возвращает
первое движение. Аналогичная логика добавлена для использования и освобождения.

[Дедупликация по текстовому reason](../src/fintracker/application/commitments/goals.py:141).
Нужен отдельный необязательный command/idempotency key, а пояснение должно
сохранить прежнюю семантику. Проверено на доменном API; обычные новые
Telegram-команды сейчас передают разные source keys, поэтому не утверждается,
что все повторные взносы из интерфейса подавляются.

Тест: `test_same_human_reason_does_not_deduplicate_distinct_goal_movements`.

### RC-06 · P1 · Минус всё ещё превращается в положительную сумму

При резерве 5000 ₽ ввод `Сумма -100` в действии «Использовать резерв» списывает
+100 ₽ и оставляет 4900 ₽. Запрет отрицательного ввода проверяет только первый
символ всей строки; парсер ниже извлекает положительные 100.
[Проверка](../src/fintracker/application/conversation/goals_flow.py:198).
Проверять знак конкретного распознанного денежного выражения либо принимать
строго определённый формат с доменным отказом для остальных форм.

Тест: `test_signed_goal_amount_with_leading_words_is_not_reinterpreted`.

### RC-07 · P1 · Новая таблица поиска обходит очистку бюджета

После создания полного поискового запроса и реального вызова
`purge_workspace_data` для удаляемого бюджета текст остаётся в
`history_query_states`. Тест подтверждает сохранение строки с назначением
и суммой платежа после успешного purge остальных данных.

В [миграции 0018](../src/fintracker/db/migrations/versions/0018_history_query_state.py:24)
нет дополнения к purge/retention; поле `expires_at` только запрещает чтение
по сроку и само ничего не удаляет. Связи с каскадом удаления бюджета тоже нет.
[Список очистки](../src/fintracker/db/migrations/versions/0011_author_replies.py:82).
Добавить контролируемую очистку истёкших запросов и включить новую таблицу
в удаление бюджета. Это дефект хранения, а не доказательство чтения другим пользователем.

Тест: `test_purge_removes_full_history_query_text`.

### RC-08 · P2 · Терминальное уведомление об удалении не отправляется

Реальный delete_workspace создаёт событие; expand_event создаёт terminal
доставки, однако worker ничего не отправляет. Начальный вызов authority
не передаёт delivery_class, а новый guard запрещает deleting/deleted, когда
класс не terminal. До проверки конкретной terminal доставки выполнение не доходит.
[Начальный gate](../src/fintracker/application/delivery/dispatch.py:400),
[условие](../src/fintracker/application/delivery/dispatch.py:347).
Нужен разрешённый путь для терминального события без разрешения обычных
финансовых доставок. Сейчас вместо отправки создаётся очередное продолжение.

Тест: `test_terminal_deletion_notification_reaches_member`.

### RC-09 · P2 · Отозванная доставка возвращается в pending

Если remove_member полностью завершён во время render_event, отправка теперь
правильно прекращается. Но ветка отказа перезаписывает отменённую доменной
командой доставку из `cancelled` в `pending`.
[Безусловный UPDATE](../src/fintracker/application/delivery/dispatch.py:535).
Нужно отличать временную недоступность от окончательного отзыва, сохранять
terminal state доставки и выполнять только условные изменения состояния.
В этом сценарии утечка сообщения не воспроизводится; сломан жизненный цикл.

Тест: `test_render_time_revocation_keeps_delivery_cancelled`.

### RC-10 · P2 · Повтор сверки журнала читает storage под workspace lock

При завершённой конкурентной смене ACL новая ветка создаёт SecurityLog через
приватный `_storage` и вызывает два чтения, удерживая `FOR UPDATE` бюджета.
Проверка реальным `SELECT ... FOR UPDATE NOWAIT` из другого соединения
дважды подтверждает занятый lock во время storage I/O.
[Ветка](../src/fintracker/application/identity/security_change.py:535).

Это нарушает явное правило ADR-04 о внешнем I/O вне транзакции: задержка
хранилища задерживает все денежные/ACL-команды бюджета и создаёт риск тайм-аутов.
Перечитывать журнал после завершения транзакции; затем заново сверять поколение
под короткой блокировкой, используя публичный контракт адаптера.

Тест: `test_journal_retry_does_not_hold_workspace_lock_during_storage_io`.

### RC-11 · P2 · Повтор открытия меняет версии неизменённого бюджета

После первого открытия повтор того же задания при неизменных данных меняет
`plan_revision/calendar_revision` с **(2,2) на (3,3)**. Прошлый уже ended период
не имеет BudgetPeriodOpened, поэтому снова попадает в pending, затем пропускается
как не текущий; в конце всё равно выполняется bump_revisions.
[Условие pending](../src/fintracker/application/planning/rollover.py:326),
[пропуск](../src/fintracker/application/planning/rollover.py:399),
[безусловный bump](../src/fintracker/application/planning/rollover.py:436).
Это создаёт ложные изменения основы плана/анализа. Завершённые старые периоды
не должны бесконечно требовать открытия, а версии должны расти по реальным изменениям.

Тест: `test_period_retry_does_not_invalidate_unchanged_plan`.

### RC-12 · P2 · Доменная ошибка по-прежнему теряет ожидаемый ввод

«Использовать резерв» → 100 при нулевом резерве возвращает корректную ошибку
превышения остатка, но pending удалён. Следующее сообщение уже не относится
к исправлению суммы. Новые строковые префиксы охватывают ошибку нуля, но не
все DomainError. [Решение по тексту](../src/fintracker/application/conversation/service.py:445).
Обработчик должен возвращать явный исход применения, а не определять успешность
по началу русского сообщения.

Тест: `test_domain_rejection_preserves_pending_amount`.

### RC-13 · P2 · Истёкший поиск молча превращается в журнал без фильтра

Поиск без совпадений → истечение серверного состояния → переход к сохранённой
странице показывает одну постороннюю операцию, которая запросу не соответствует.
Отсутствующая строка разрешается в `None` и уходит в list_journal как отсутствие
условия. [Разрешение токена](../src/fintracker/application/conversation/history_flow.py:113).
Нужен явный ответ об истечении состояния с предложением повторить поиск;
нельзя незаметно менять состав финансовой выборки.

Тест: `test_expired_history_query_does_not_silently_remove_filter`.

## Остатки предыдущего аудита

- Compose по-прежнему не задаёт DB DSN для api/worker/scheduler. Эффективные
  defaults направлены на `localhost:55432`, а соседняя БД доступна как
  `postgres:5432`. Это подтверждено разбором конфигурации; новый Docker-образ
  и запуск всего стека в этом проходе отдельно не проверялись.
- `make trace` отклоняет сохранённый `.planning/evidence/latest.json` от
  `6ed8112`. Новые диагностические результаты сохранены отдельно; автоматически
  приписывать им старые `verified` нельзя.
- Интерфейс `/members` не добавил исключение/разрешение повторного входа;
  фильтры истории по-прежнему показывают только первые четыре категории и не
  дают полного выбора другого автора/покупателя/получателя. Это статическая
  повторная проверка известных пробелов, не новые динамические случаи в таблице.
- Полный размеченный AI/ASR/чековый корпус, реальные интеграции, внешний пилот,
  WAL/PITR и S3 backend не подтверждены этим проходом. Проверки на управляемых
  адаптерах не заменяют такую приёмку.
