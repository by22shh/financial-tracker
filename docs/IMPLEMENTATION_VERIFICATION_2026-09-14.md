### V-01. Немедленная отправка обходит проверку актуального доступа

**Сценарий:** участник запрашивает `/history`; история уже сформирована; администратор завершает `remove_member`; исходный обработчик продолжает доставку ответа.

**Результат:** исключённому участнику отправлена история с датой, категорией и суммой **98 765 ₽**. Отложенный путь теперь проверяет доступ, но непосредственный вызов `_send_now` этого не делает. Изоляция `author_replies` по бюджету и владельцу сама по себе не подтверждает действующее членство.

Код: [финальная немедленная отправка](/Users/Bayramov_N/Desktop/Other/financial-tracker/src/fintracker/application/ingestion/process_event.py:592). Проверка: `test_immediate_reply_rechecks_revocation`.

**Исправление:** все финансовые ответы должны проходить общий этап проверки адресата непосредственно перед отправкой: актуальное членство, поколение, состояние бюджета, карантин и fence. Отказ должен отменять подготовленную доставку. Проверить оба пути отправки при отзыве доступа после формирования текста.

### V-02. Идентичность исходного сообщения не передаётся в обработку фото и голоса

**Сценарий:** обработан один Telegram Update с фото; после сохранения карточки и задания доставки процесс прерывается; тот же вход обрабатывается повторно. Затем подтверждаются обе сохранённые карточки.

**Результат:** **два черновика с `source_message_key = NULL` и две проведённые траты по 450 ₽**. Второе проведение требует подтверждения карточки — это не автоматический дубль текстовой траты из прежнего P0. Однако обе карточки относятся к одному исходному сообщению, и каждая остаётся самостоятельно доступной для подтверждения.

Новый ключ используется текстовым обработчиком. В `media_pipeline` при создании черновиков фото и голоса не передаются ни `source_message_key`, ни идентификатор исходного события. Хеш изображения не обеспечивает уникальности черновика.

Код: [создание черновика фото](/Users/Bayramov_N/Desktop/Other/financial-tracker/src/fintracker/application/intelligence/media_pipeline.py:215), [аналогичный вызов для голоса](/Users/Bayramov_N/Desktop/Other/financial-tracker/src/fintracker/application/intelligence/media_pipeline.py:81). Проверка: `test_repeated_photo_event_reuses_its_draft`. Финансовый дубль воспроизведён для фото; голосовой путь отмечен по коду, без заявления о выполненном ASR-тесте.

**Исправление:** распространить постоянную идентичность ввода на медиа, повторно использовать прежний черновик и его результат. Проверять повтор после сохранения карточки, а также после её подтверждения. Подтверждение повторно показанной карточки должно возвращать прежнюю операцию.

### V-03. Execution fence не защищает обработчики, которые не вызывают `lock_workspace`

**Сценарии:**

1. Во время ожидания AI изменяется `Job.lease_token`; результат модели возвращается старому исполнителю.
2. Во время ожидания AI бюджет переводится в карантин.
3. Задача отложенной доставки получает истёкшую аренду; обработчик выполняется с установленным `execution_fence`, как в worker.

**Результат:** в первых двух случаях анализ сохраняется как `succeeded` и публикует события завершения. В третьем случае финансовый ответ отправляется. Само наличие ContextVar не выполняет проверку: её вызывает только `UnitOfWork.lock_workspace`, которого в этих путях нет.

Код: [сохранение анализа](/Users/Bayramov_N/Desktop/Other/financial-tracker/src/fintracker/application/intelligence/analysis.py:490), [обработчик отложенного ответа](/Users/Bayramov_N/Desktop/Other/financial-tracker/src/fintracker/application/ingestion/process_event.py:423). Проверки: `test_analysis_rechecks_authority_after_model[lease]`, `[quarantine]`, `test_expired_lease_cannot_send_deferred_reply`.

**Исправление:** проверять право на результат в каждой транзакции, принимающей результат фонового задания, включая анализ и fallback. Перед внешней отправкой нужна отдельная проверка действующей аренды и адресата. Проверка должна выполняться фактически, даже если обработчик не пользуется обычной командой изменения бюджета. Вызов модели следует сохранить вне транзакции.

### V-04. Подготовленный анализ не восстанавливается после прерывания

**Сценарий:** `_prepare_analysis` сохраняет строку со статусом `running`; процесс прерывается на вызове модели; новый исполнитель повторяет тот же `logical_key`.

**Результат:** `_prepare_analysis` возвращает существующий результат со статусом `running`, не продолжая работу. Обработчик задания считает такой статус основанием завершить выполнение без доставки. Планировщик также исключает ключи, для которых уже существует любая строка `AnalysisRun`. Обзор за этот логический период потерян до отдельного вмешательства.

Код: [безусловный возврат существующего запуска](/Users/Bayramov_N/Desktop/Other/financial-tracker/src/fintracker/application/intelligence/analysis.py:344). Проверка: `test_analysis_resumes_after_process_interruption`. Прерывание моделируется `CancelledError`; повтор выполняет штатный сервис, результат — снова `running`.

**Исправление:** различать завершённый результат, действующий запуск и незавершённый запуск утратившего аренду исполнителя. Новый владелец должен иметь возможность продолжить анализ или завершить его явным восстановимым отказом. Для уже завершённых запусков нужно сохранять достаточно результата, чтобы повтор мог завершить недоставленную сводку.

### V-05. Сверка доступа при обычном старте использует владельца миграций

**Сценарий:** в БД уже есть бюджет; API и worker DSN доступны; приложение запускается без подключения владельца миграций.

**Результат:** runtime readiness проходит, но реальный lifespan API завершается ошибкой подключения: `reconcile_access_on_start → resume_or_quarantine` открывает `RuntimeRole.OWNER`. Worker вызывает ту же цепочку. Это нарушает зафиксированное правило ADR-06: «Владелец миграций не используется приложением».

Код: [OWNER-сессия](/Users/Bayramov_N/Desktop/Other/financial-tracker/src/fintracker/application/identity/security_change.py:444), [старт API](/Users/Bayramov_N/Desktop/Other/financial-tracker/src/fintracker/api/app.py:26), [старт worker](/Users/Bayramov_N/Desktop/Other/financial-tracker/src/fintracker/runtime/worker.py:135), [ADR-06](/Users/Bayramov_N/Desktop/Other/financial-tracker/docs/ARCHITECTURE.md:140). Проверка: `test_api_start_does_not_require_migration_credentials`.

В пробе намеренно недоступен только migration DSN. Перед запуском lifespan отдельно подтверждена работоспособность API-подключения. Это не общая недоступность PostgreSQL.

**Исправление:** выполнять автоматическую сверку через ограниченную runtime-роль и узкие разрешённые операции. Действия, которым действительно нужен владелец схемы, должны относиться к отдельной процедуре восстановления. Проверять полноценный старт процессов с production-набором полномочий, а не только вызов функции readiness.

### V-06. Успешный downgrade `0011` ломает очистку удалённых бюджетов

**Сценарий:** схема обновлена до `0011_reply`; выполнен `alembic downgrade 0010_input`; вызывается штатная `purge_workspace_data` для удалённого бюджета.

**Результат:** downgrade возвращает exit 0, но функция падает с `UndefinedTable: relation "author_replies" does not exist`. Миграция меняет тело функции при upgrade, а при downgrade удаляет таблицу без восстановления прежнего тела функции.

Код: [downgrade 0011](/Users/Bayramov_N/Desktop/Other/financial-tracker/src/fintracker/db/migrations/versions/0011_author_replies.py:137). Проверка: `test_downgrade_keeps_previous_purge_function_usable`. После пробы схема возвращена на head в отдельной тестовой БД.

**Исправление:** восстанавливать предыдущие определения всех изменённых SQL-функций при откате. Проверка обратимости должна выполнить операцию предыдущей версии между downgrade и upgrade. Один exit 0 обеих команд не доказывает работоспособности откатившегося приложения.

### V-07. Конкурентный конфликт приводит к работе в закрытой транзакции

**Сценарий:** оба исполнителя успели проверить отсутствие черновика; один выигрывает вставку в новый уникальный индекс; второй получает `IntegrityError`.

**Результат:** одна трата действительно сохраняется, но второй исполнитель получает `InvalidRequestError: Can't operate on closed transaction inside context manager`. После `session.rollback()` код пытается читать прежний черновик внутри уже закрытого `session.begin()`.

Код: [rollback и последующее чтение](/Users/Bayramov_N/Desktop/Other/financial-tracker/src/fintracker/application/conversation/entry.py:545). Проверка: `test_both_concurrent_executors_return_a_result`.

Прежняя проверка параллельности пропускает эту ошибку: `asyncio.gather(..., return_exceptions=True)` не проверяется, проверяется только число трат. Новый уникальный индекс защищает деньги; замечание P2 относится к обработке конфликта и обещанному ответу второго исполнителя.

**Исправление:** использовать корректный `ON CONFLICT`, savepoint либо новую транзакцию с повторной установкой RLS-контекста. В конкурентном тесте проверять и финансовый инвариант, и результат каждого вызова.

Код: [первое событие](/Users/Bayramov_N/Desktop/Other/financial-tracker/src/fintracker/application/intelligence/analysis.py:552), [повторное событие](/Users/Bayramov_N/Desktop/Other/financial-tracker/src/fintracker/application/intelligence/schedule.py:280). Проверка: `test_successful_summary_emits_one_completion_event`. Проверено количество событий в БД; настоящий Telegram не вызывался.

**Исправление:** назначить одному этапу ответственность за событие завершения и обеспечить уникальность публикации для логического запуска. Успех модели и fallback должны проходить тот же контракт публикации.

### V-09. Проверка `verified` всё ещё допускает отсутствие доказательств прогона

Старая подмена несуществующего узла и файла теперь корректно отвергается. Но два соседних случая проходят:

При пустом `outcomes` проверка всех узлов пропускается. Commit проверяется только при наличии обеих строк. Записанная SHA256 JUnit не сверяется с содержимым файла, поэтому подмена пустым отчётом не обнаружена и по хешу.

Код: [пропуск проверки пустого набора](/Users/Bayramov_N/Desktop/Other/financial-tracker/.planning/tools/check_traceability.py:243), [условная проверка commit](/Users/Bayramov_N/Desktop/Other/financial-tracker/.planning/tools/check_traceability.py:181). Доказательство: [traceability-probes.json](/Users/Bayramov_N/Desktop/Other/financial-tracker/.planning/audits/2026-09-14-verification-enqwqlik/traceability-probes.json).

**Исправление:** отсутствие результатов и идентификатора версии должно отклонять `verified`; необходимо проверять хеш и соответствие проверяемым исходникам. Отдельно учитывать изменения конфигурации/зависимостей и незакоммиченный код: текущий `git diff revision..HEAD -- src tests` их не покрывает. Последние два ограничения установлены чтением кода, а не выданы за дополнительные выполненные пробы.

## 4. Измерения и заявленные ограничения

- На 50 000 операций отчёт показал p95 **0,3505 с**, журнал с фильтрами — **0,2725 с**. Это локальная проверка в условиях данного прогона.
