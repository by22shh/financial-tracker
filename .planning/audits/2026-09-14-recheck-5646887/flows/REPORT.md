### FLOW-R01 — P1 / BLOCKER: отмена диалога не отменяет pending action

**Сценарий:** `/goals` → «Добавить цель» → `/cancel` → `продукты 450`.

**Ожидается:** отменённое создание цели больше не перехватывает сообщения; появляется обычный расход/черновик 450 ₽.

**Фактически:** `Цель «продукты 450» на 450,00 ₽ создана`; в БД Goal с таким именем, ни одной TransactionRevision. Расход как расход потерян.

**Причина:** [service.py:259](/Users/Bayramov_N/Desktop/Other/financial-tracker/src/fintracker/application/conversation/service.py:259) отменяет только Draft/Candidate; `clear_pending` в [pending.py:91](/Users/Bayramov_N/Desktop/Other/financial-tracker/src/fintracker/application/conversation/pending.py:91) не вызывается из conversation вообще. Следующий текст попадает в прежний `goal_new` через `_continue_pending`.

**Доказательство:** `test_cancel_clears_goal_creation_before_next_expense`.

**Исправление:** включить все виды ожидаемого ввода в `/cancel` и кнопочную отмену; явно завершать / отменять состояние и тестировать следующее обычное сообщение. Требования: FR-20, FR-49, управление незавершённым вводом; общая регрессия механизма G-13…G-16.

### API Coverage / Auth Protection

В этом scope внешняя граница — Telegram, внутренние API — conversation handlers. HTTP routes/webhook проверяет основной аудитор. Создание сущностей выполняется через load_actor и API/RLS, денежные изменения — через lock_workspace. В новом воспроизведении смены бюджета доступ к чужому бюджету не получен: нарушена адресация внутри двух разрешённых бюджетов. Исправление G-18 применяет предложение к текущему получателю; исключение участника отсутствует как доступное действие, а не как защищённая API-функция.
