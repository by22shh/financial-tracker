# Контракт API, выпуск и достоверность доказательств

Проверен commit `7a56769`. Продуктовые исходники и прежние доказательства не изменены.

## OPS-A — P1: схемы Structured Outputs не соответствуют контракту OpenAI

`src/fintracker/infra/ai/schemas.py:220–224` возвращает обычный Pydantic JSON Schema
с необязательными полями; `openai_client.py:127–132` отправляет его с `strict: true`.
У `ExtractionResponse` корень не требует `candidates`/`question`, вложенный
`ExtractionCandidate` не требует суммы, валюты и прочих полей. Та же проблема
у `ReceiptResponse`, `RecommendationResponse`, `AnalyticsPlan`.

[Официальный контракт](https://developers.openai.com/api/docs/guides/structured-outputs#all-fields-must-be-required)
требует все properties включать в required, необязательность выражается nullable.
Локальная проверка фактически генерируемых четырёх схем провалилась на каждой.
Живой HTTP 400 не выдаётся за измерение: платный вызов не выполнялся; несовместимость
установлена сопоставлением запроса с документированным контрактом.

Эффект: подключение ключа само по себе не обеспечивает работу AI-разбора и анализа.
Нужна рекурсивная нормализация схем, проверка исходящего HTTP payload и живой smoke
на выбранной модели. `AI-03`, `ADR-08`, `ADR-17`, `FR-13/14`, `FR-73`.

Выбранный `gpt-5.6-luna` и medium подтверждаются
[официальной карточкой модели](https://developers.openai.com/api/docs/models/gpt-5.6-luna).
Это не подтверждает наличие доступа у конкретного аккаунта.

## OPS-B — P1: контейнер ready, но штатные файловые backend не запускаются

`Dockerfile:46–47` устанавливает WORKDIR `/app` и пользователя UID10001, но не создаёт
записываемые каталоги. `config.py:182,193` задаёт `./var/objects` и
`./var/security-log`; оба конструктора делают mkdir. В текущем пересобранном образе
вызовы `build_storage(Settings().storage)` и `build_security_log(...)` дают
`PermissionError: Permission denied: 'var'`.

`check_readiness` проверяет БД/схему, поэтому прежнее `ready:true` этого не обнаруживало.
Создание бюджета и экспорт требуют этих backend. Команда запуска без volume/настройки
прав из FINAL_REPORT не достаточна. Нужны записываемые persistent mounts, единый доступ
api/worker/scheduler к ним и smoke полного создания бюджета/выгрузки из контейнера.
Кроме того, единый HEALTHCHECK обращается к API:8080 даже для worker/scheduler, у которых
такого сервера нет. `OPS-01/02/06`, `ADR-01/11/14`.

## OPS-C — P1: воспроизводимый checkout отклоняется CI, новый JUnit не используется

`evidence_source.py:75–80` включает игнорируемые `.DS_Store`. Они попали в сохранённый
manifest, но отсутствуют в Git и Linux checkout. На чистом `git archive HEAD` checker
даёт exit1 «содержимое отличается». Рабочая копия того же commit даёт exit0.

Также CI пишет `.planning/evidence/junit.xml` (`ci.yml:80`) и затем читает прежний
`latest.json` через checker (`ci.yml:83`); collector, формирующий новое metadata,
там не запускается. Старый `latest.json` ссылается на `latest-junit.xml`, не CI junit.xml.
Нужны переносимый manifest исходников и привязка CI к своему свежему прогону, включая
явную обработку измерений, которые без FINTRACKER_PERF пропускаются.
`QA-01/02`, `OPS-04`, достоверность статусов verified.

## OPS-D — P1: проверяется метаинформация изображения, а не его байты

`conversation/media.py:76–108` доверяет MIME/размерам из Attachment. После загрузки
`intelligence/media_pipeline.py` делает data URL и вызывает vision без проверки сигнатуры,
реального разрешения и безопасного декодирования. Файл с MIME image/jpeg и содержимым
обычного текста дошёл до ScriptedAIProvider через штатный handle_media с реальной RLS.
Строгая проверка «повреждённый файл отклонён до платного вызова» упала.

Существующий `test_qa02_corrupted_image_is_rejected_before_paid_call` проверяет
запрещённый MIME/объявленный размер, не этот случай. Нужны проверки скачанных байтов и
лимитов до provider call. `SEC-07`, `NFR-11`, `LIM-09`, `ADR-11`.

## OPS-E — P2: нагрузочные цифры и verified не доказывают заявленный объём

- `test_performance.py:263` выполняет 30 секунд при5/с вместо10минут. Всплеск —5 пакетов
  по20без30секунд заданного профиля. Полный baseline принимает250событий вместо3600.
- Строки273/287 делят длительность конкурентного пакета на5/20. Это не задержка одного
  запроса: при20запросах, каждый из которых занял2с, тест запишет0,1с.
- `test_nfr08_concurrent_workspaces:319–328` последовательно создаёт бюджеты/проводит траты;
  это не проверка одновременной работы10×5.
- AI-04:36текстов+19защитных входов проверяют детерминированный парсер; набор §25.1
  требует250/100/100/50. Качество GPT/OCR/ASR на этом не измерено.
- NFR-13 «мониторинг метрик» ссылается только на тест редактирования секретов в логах.
  В runtime не найден сбор возраста очереди/backup и требуемые операционные оповещения.
- AI-06 «план запроса аналитики» ссылается на проверку отказа рекомендации без metric_ref,
  то есть другого контракта. AR-36 ссылается на тест разделения стадий ошибок, не корпус.

Даже текущий успешный checker доказывает существование/прохождение тестов и соответствие
байтов, но не смысловую полноту требования. Число481verified нельзя считать96,2%готовности.

## Доказательства

- `contracts.json`: четыре схемы, ошибки каталогов контейнера, провал чистого checkout.
- `*.schema.json`: точные генерируемые схемы.
- `test_contract_readiness.py`, `run_probes.py`, `pytest.log`, `junit.xml`:5проваленных
  независимых утверждений о требуемом поведении (4контракта+1повреждённое изображение).
- `requirement_states.json`: полный список19требований, не имеющих verified даже по реестру.
